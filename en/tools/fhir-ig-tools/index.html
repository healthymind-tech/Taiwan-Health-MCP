    FHIR IG Tools¶

    A general, IG-scoped toolset built on the multi-IG fhir.* store, used to explore Implementation Guides, read profiles and terminology, perform terminology validation, and produce and validate FHIR R4 resources through skeleton-fill authoring.

    Maintenance mode: while the admin console has the ig module in maintenance mode, all 22 tools of this group (including fhir_check_grounding / fhir_check_completeness) calls return an isError result immediately with error code MODULE_MAINTENANCE (error.message in English, error.message_zh in Traditional Chinese, error.module the module key), effective within about 5 seconds; the tools stay in tools/list. See the API reference.

    Shared conventions¶

    • Every tool accepts an optional package_id + version. When package_id is omitted, the target package is chosen by this precedence, and provenance.resolved_by says which rule applied:
      1. explicit_version — a canonical argument or meta.profile pinned as url|version → the package holding that version;
      2. package_arg / latest — package_id was given (with version, that version; without it, the default IG's version, else the highest release — pre-releases only when no release exists);
      3. meta_profile / canonical_owner — the package that owns the meta.profile or the canonical argument (profile / ValueSet / system), manually-installed IGs first;
      4. default_ig — the default IG (isDefault);
      5. sole_manual_ig — no default IG and exactly one manually-installed IG. If none applies the call fails with NO_DEFAULT_IG (no arbitrary package is picked).
    • A |version is always honoured: a version that is not installed returns ARTIFACT_NOT_FOUND (the message lists the installed versions) — never a silent fallback to another version.
    • Responses use a shared envelope: {ok, data, warnings, provenance, error?}. provenance carries packageId / version / fhirVersion / source plus resolved_by; when the dependency closure holds several versions of one package it also carries closure_versions (which version canonical lookups use).
    • When declared dependencies of the target IG are not installed, data.deps_missing lists them as {package_id, version, required_by} (incomplete closure — results may be missing content).
    • List / search tools (fhir_list_artifacts, fhir_search_artifacts, fhir_list_resource_profiles) query only the default IG when package_id is omitted; all_packages=true queries every installed package instead (rows carry package_id / package_version; package_id is then ignored). Zero hits come with data.hint naming the other packages that match.
    • Compact output compact=true (fhir_list_igs, fhir_list_artifacts, fhir_search_artifacts, fhir_list_resource_profiles; default false, and the default output is unchanged) is for LLMs with a tight tool-output budget. Each type becomes an {id: title} map, the common canonical prefix is written once (canonical_base; canonical = canonical_base/<ResourceType>/<id>), and only canonicals that break that rule are listed in canonicals; profiles also list non-active ones in status; data.compact is a one-line reading guide. With all_packages=true the groups sit under packages (packageId#version → that package's group). fhir_list_igs returns default plus manual / dependency maps by install origin (packageId#version → title). Measured on TW Core: fhir_list_resource_profiles 12.9k → 4.8k characters, fhir_list_artifacts (50 rows) 19.9k → 2.8k, fhir_search_artifacts (20 rows) 8.6k → 1.5k, fhir_list_igs (58 packages) 19.6k → 3.7k.
    • For the module concepts and the suggested workflow, see FHIR IG Service.

    Derived elements and Must Support¶

    Elements with grounding_class: "derived" are not copied from the record but follow from other filled values. For well-known derived elements, hint starts with derive: and states the rule (each rule paraphrases the published definitions of the codes it names; the citation is derivation_source in verbosity="full"). A rule applies only when the element's binding is the ValueSet the rule describes:

    Element Rule (summary) Source
    Condition.category diagnosed or assessed in this visit (outpatient, admission, discharge) → encounter-diagnosis (and point Condition.encounter at that encounter); an entry of the longitudinal problem list kept across visits → problem-list-item; a diagnosis written in a visit note is encounter-diagnosis even when the disease is chronic FHIR R4 condition-category; US Core Condition Encounter Diagnosis / Problems and Health Concerns
    Observation.category by what was measured: lab test → laboratory, BP / heart rate / temperature / height / weight … → vital-signs, imaging, exam, survey, social history … FHIR R4 observation-category; R4 Vital Signs profile
    Encounter.diagnosis.use / .rank admission AD, discharge DD, chief complaint CC, comorbidity CM …; principal diagnosis rank 1, the rest in record order FHIR R4 diagnosis-role; Encounter.diagnosis.rank
    MedicationRequest.category / MedicationStatement.category / courseOfTherapyType by the setting of the order (inpatient / outpatient / community / discharge); long-term continuous, short course acute FHIR R4 code systems
    AllergyIntolerance.category / .type / .criticality, Observation.interpretation by the substance; immune vs non-immune reaction; life-threatening → high; against the reference range N / H / L / HH / LL FHIR R4 code systems

    Derived elements without a rule get the CodeSystem definitions of the binding's codes in hint (pick the code whose meaning fits the record: …).

    mustSupport is not required. include_mustsupport="defaults" adds only the mustSupport elements that need no source fact (a profile fixed value / pattern, a conventional default such as verificationStatus, a derivable value from the table above) and whose parents are all listed; true adds every mustSupport element. Rows added either way carry optional: true and a "may be left out, never refuse over it" hint, and guide says the same. The default (false) output is unchanged except for the derived rows.

    fhir_validate_resource / fhir_validate_bundle also report whether validation was complete: checked_fully (true when every check HL7 validator_cli would do was done here), profiles_unchecked, valuesets_unchecked. valid keeps HL7 semantics, so valid: true with checked_fully: false means some check validator_cli would do was not done here (for example a code system it asks its terminology server about and that has no local data). Where validator_cli itself only warns (no CodeSystem found, an unknown profile) the same warning is returned and checked_fully stays true; those cases are judged by extended_findings. When definition / terminology lookups failed during the run because of database trouble, lookups_failed (the count) is added; such a run always carries an error issue with code: "exception" and valid is false (1.6.1). |version canonicals (meta.profile, binding, targetProfile, type profile, extension url) are resolved like HL7 validator_cli 7.0.1.

    The builtin validator also checks, like HL7 validator_cli 7.0.1 (same release, 1.6.0):

    • Where an extension may be used: the extension definition's context (element / extension types; contexts restricted to other FHIR versions by version-specific-use are skipped) and contextInvariant. A violation is an error at the host element: The extension <url> v<version> is not allowed to be used at this point (this element is [...]; allowed for this version = e:...) or ... (based on context invariant '...'). fhirpath contexts are not evaluated locally (never an error).
    • An unversioned StructureDefinition resolves to the highest-version copy in the closure (e.g. the hl7.fhir.uv.extensions.r4 extension over the R4 core one with the same URL), so the extension's own invariants (e.g. var-1 of variable) are checked too.
    • Unrecognized property is judged against the core definitions for the whole resource (as the HL7 JSON parser does), including below a choice type the profile does not allow and inside the value of an unknown extension; like HL7, nothing is checked below an element with the wrong JSON shape (an array for a single element).
    • RxNorm: code and display are checked against rxnorm.concepts (tx.fhir.org accepts every SAB=RXNORM name of the RXCUI, case-insensitively): Wrong Display Name '...' for http://www.nlm.nih.gov/research/umls/rxnorm#<code>. Valid display is '...'. An unknown code is an error only when the local RxNorm release is not older than tx.fhir.org's (03022026), otherwise a warning; when only the preferred name is held (imported before migration 20261030) a display mismatch is a warning; without RxNorm loaded: warning Display not checked (RxNorm).
    • Unknown code in an IG CodeSystem with content = complete stays an error; when another installed package has a fuller copy of the same CodeSystem containing the code (e.g. TW Core 0.3.2 medication-nhi-tw), an information issue names that package and version.
    • Unknown-code suggestions (v15.2): a replacement code of an IG CodeSystem must be related to the original — a shared linked code (the same ATC), a shared rare word (an ingredient, not a dose form or salt) or a near-identical name, at the same strength; when none is related, none is given (no more Amlodipine → unrelated-drug suggestions).     IG known defects (v17.3)¶

    Some profiles cannot be met even by the IG's own examples. For example, TWPAS Condition-twpas slices Condition.code.coding by pattern $this, but its slices carry only bindings and no pattern, so no coding matches a slice — and the slicing is closed. No instance written like the examples can ever be valid.

    • Detection: the background job ig_selfcheck (admin "IG 範例自我檢查") runs after every IG import, and when the worker starts for packages not yet checked. It validates every example of a package (the entries of its example Bundles included) against the package's own profiles they declare, using the local validator. An error at the same element under the same structural rule (slicing, cardinality, unknown elements, fixed / pattern) in every example of a profile is a known defect of that profile (known_invalid). These are not counted: errors caused by the examples' own values (example.org identifiers, formats, date invariants), errors that depend on local terminology or references, and entries an example Bundle happens to hold. Results are stored in fhir.ig_known_defects.
    • fhir_get_bundle_blueprint: known_invalid lists such slices with the reason, the example files, and where the information goes instead — a CodeableConcept of another slice's profile bound to the same ValueSet, e.g. claim: diagnosis.diagnosisCodeableConcept — and asks you to leave out the references to it too.
    • fhir_get_minimal_skeleton / fhir_get_authoring_fields: the same note in warnings.
    • fhir_validate_*: a matching error gets ig_known_defect, plus a note at the end of its message (the entry is likely optional; where its information goes). Severity, the issue set and valid are unchanged.

    Parity with the official validator (parity v1)¶

    fhir_validate_bundle / fhir_validate_resource judge as HL7 validator_cli 7.0.1 (with tx.fhir.org) does. The rules below are ported from the official source (org.hl7.fhir.core 7.0.1):

    • bundle_profile argument (fhir_validate_bundle): as validator_cli -profile, the Bundle is validated against it as well as its meta.profile. Pass the conversion target's Bundle profile; without it only meta.profile is checked, and MCP does not guess one.
    • Parser stage (JsonParser): unknown properties and JSON shape errors (array / object / primitive) are reported once, judged by the base definition, with the official messages. Later profile matching — slices by profile, reference target profiles — does not see them. An element left with only unknown properties fails ele-1.
    • Choice types: a type the base element does not allow is an Unrecognized property. A type the base allows but a profile that fixes another single type does not gives Extension_PROF_Type (Extension_EXT_Type for an extension), and the value is validated as the profile's type. When a profile defines children for a multi-type choice, the actual type's children apply too.
    • Value sets: a required-bound code whose CodeSystem cannot be inferred gives The System URI could not be determined …. A member with a wrong display fails the binding, as tx $validate-code does.
    • fixed / pattern: compared field by field as the official checkFixedValue does, with its messages.
    • Other: the same rule from different profiles is reported once per profile. A document whose first entry is not a Composition gets The first entry in a document must be a composition, and reachability is still checked.

    Regression: on the evaluator's 92 reproducible Bundles (PAS + IPS), the error classes agree with the official validator 100% (0 missed, 0 extra); the 28-Bundle IPS set and the 4 language variants agree as well. What needs a terminology server (SNOMED is-a value sets, all-LOINC value sets, tx display candidates) is left to the v18 official final check.

    Document Bundle parity (v17.5)¶

    In production there is no official validator: what MCP calls valid is sent. Document Bundles must therefore be judged as HL7 validator_cli 7.0.1 + tx.fhir.org judge them. v17.5 adds these rules:

    • References inside the Bundle: in a document / message Bundle, every reference of every entry other than the Composition must resolve inside the Bundle (the HL7 fullUrl rules, with no type/id fallback). An unresolved one is an error on Bundle, "Can't find '…' in the bundle (Bundle.entry[n].resource.…)", with the fullUrl to use when a resource of that type and id is there under another fullUrl. Such an entry is then also unreachable from the Composition (an error).
    • Local narrative links: an <a href="#x"> with no matching anchor is an error. An anchor can be an id / name in any narrative of the Bundle, or a resource id. The resource then also fails its profile — and so any slice matched by profile — as with the official validator.
    • url|version uris (e.g. Coding.system = http://…/v2-0360|2.7): the version must resolve, else an error.
    • Displays in non-English resources: when a resource's language is not English (e.g. zh-TW) and a coding is bound to a ValueSet that enumerates its codes (SNOMED CT, LOINC), tx.fhir.org accepts only the display the ValueSet lists (e.g. "Pertussis (disorder)" in IPS target-diseases-uv-ips), and any other display is an error. Probed with validator_cli: zh-TW / fr-LU give errors, en-US or no language do not.
    • LOINC displays: tx.fhir.org uses LOINC 2.83. While the local LOINC is older, the bundled data/terminology/loinc-tx-display.json.gz is used instead — 2,264 renamed codes, e.g. 30954-2 "…Narrative" → "…note", plus LOINC's DisplayName — for validation and the display repair. Once LOINC 2.83 or newer is imported, the local data is the source again.

    Comparison: on the 4 IPS 1.1.0 examples and their variants (wrong section displays, entries not referenced from a section, urn:uuid fullUrls with relative references), the same after fhir_finalize_bundle (28 Bundles in all), plus 4 language variants, MCP and validator_cli report exactly the same errors: 0 missed by MCP, 0 extra.

    Document Bundle completion (v17.1)¶

    When fhir_finalize_bundle runs with repair="content" (as fhir_assemble_bundle always does), and Bundle.type is document or the Bundle profile fixes it, the Bundle is completed deterministically from the Composition profile:

    • Bundle.identifier: added when absent (urn:ietf:rfc:3986 + a UUID v5 of the Composition; the same document gets the same id). Bundle.timestamp: added only when Composition.date has a time with a UTC offset; otherwise reported — the time is never invented.
    • Composition.subject / author: added when absent and the Bundle holds exactly one candidate (a Patient; a Practitioner, else an Organization). When the Composition declares no profile, meta.profile is taken from the Bundle profile's composition slice.
    • Sections: the Composition profile's section slices are read (code pattern, title / text minimums, entry target profiles). Every entry not reachable from the Composition is placed into the one section that takes it. The decision goes, in order: its declared profile; the codes the target profile pins and its required code binding; the resource type. A required section with no entry yet comes first. A missing section is created, with the code display from the pattern or the terminology, the title from that display, and a text generated from its entries' names. A missing required section, or an entry several sections could take, is reported — no empty section is created, because an emptyReason is a record fact.
    • Narratives (every resource and section): a text without a div gets one from the string it carries; a div without the XHTML namespace gains it; an invalid status (such as final) becomes generated; a local link to no anchor loses its <a> tag and keeps its text (v17.5).
    • v17.5: a section code pinned by the Composition profile gets the terminology's display; a section with an emptyReason takes no entries (reported instead); a Coding.system written as url|version has the version moved to Coding.version.

    Bundle finalisation (fhir_finalize_bundle / normalize_ids)¶

    Models — weaker ones especially — write readable but malformed identities: fullUrl: "urn:uuid:patient-1", references as Patient/patient-1 or a bare id, Bundle.id as a urn. None of this is clinical content, yet the official validator rejects the whole Bundle. fhir_finalize_bundle hands that numbering-and-wiring work to the tool. Every rule comes from the FHIR R4 core specification or from the package's StructureDefinitions — nothing is special-cased per IG:

    Rule What it does
    fullUrl-uuid (mandatory) Valid values are kept (lowercase urn:uuid:<UUID>, urn:oid:, absolute http(s)://); an uppercase UUID is lowercased; anything else (a label, missing, empty) gets a deterministic UUID v5: fixed namespace, seeded by (resourceType, original fullUrl, resource.id, entry position) plus a Bundle-level salt (SHA-256 of the Bundle with the rewritable fields stripped), so the same input always yields the same output and different Bundles never collide
    reference-rewire (mandatory) Every Reference-typed element is located through the resource's StructureDefinition snapshot (the profile when meta.profile resolves, else the core definition) — including extension valueReference (definition resolved by url / slice), Composition.section.entry, Provenance.target, datatype children such as Identifier.assigner, backbone elements and contained resources. The original fullUrl, a case-different UUID, Type/id (matching resource.id) and a bare id all map to the same entry and are rewritten to its final fullUrl. A bare id / type-less form that matches several entries is disambiguated by the element's targetProfile types; still ambiguous or missing → listed in unresolved with same-type entries as candidates, never guessed. #contained, absolute URLs outside the Bundle and identifier-only logical references are left alone; …/_history/v is resolved with the version kept
    resource-id (mandatory) A resource.id / Bundle.id outside [A-Za-z0-9\-.]{1,64} takes its last segment (urn:uuid:… → the UUID); if still invalid, resource.id becomes the entry's UUID and Bundle.id a generated value
    bdl-7 Duplicate fullUrls are only reported (notes), never merged or dropped; references to a duplicated label become unresolved with both candidates
    bundle-type / document-order (profile-driven, or requested by the caller) When the StructureDefinition of bundle_profile (or meta.profile) fixes Bundle.type (fixed / pattern) it is set; a caller-supplied bundle_type (R4 bundle-type code) is applied as rule bundle-type with reason: "requested by caller (bundle_type)", but a profile-fixed type always wins (the conflict is only noted); for type=document the Composition is moved to the first entry. A document with no Composition at all is never retyped on its own: notes names both ways out — bundle_type=<the type the entries' shape supports> or adding a Composition. Elements the profile requires with real values (Bundle.identifier, Bundle.timestamp …) are only reported in notes, never generated

    Apart from those fields the output Bundle is identical to the input (deep copy, key order preserved), numbers included: the HTTP layer parses the request with JSON.parse, which turns 10.0 into 10, 1e3 into 1000 and rounds integers beyond 2^53, while a FHIR decimal's precision is part of its value. So fhir_finalize_bundle, the normalized_bundle of fhir_validate_bundle(normalize_ids=true), the entry resources of fhir_build_bundle and the resource of fhir_finalize_resource re-read the bundle / entries / draft argument losslessly from the raw request text; the finalisation still runs on the ordinary tree (UUIDs, changes and validation are unchanged) and only at the end is each number swapped back to the caller's spelling (10.0, 1.50, 0.50, -0.0, 12345678901234567890, inside extensions and nested arrays too; only where the value is the same). All three entry points (/mcp, POST /tools/<name>, the admin console playground) return the same bytes. An already valid Bundle is returned unchanged with changes: [], and finalising a finalised Bundle changes nothing. Without package_id the package is resolved from bundle_profile / meta.profile; when no IG resolves, hl7.fhir.r4.core is used.

    fhir_validate_bundle shares the engine: by default (normalize_ids=false) ID-class errors carry suggestions (replace_fullurl / replace_reference / replace_id / move_entry / replace_bundle_type) and data gains the full map id_map (old → new), id_changes (every path that must change together) and id_unresolved; a Bundle without ID-class issues is byte-identical to 1.6.1. With normalize_ids=true the Bundle is finalised first, the normalised Bundle is validated and returned as normalized_bundle with id_changes, and each fixed problem is noted as an information issue. fhir_get_profile_required_elements on a Bundle profile additionally returns bundle_rules (fullUrl format, references = the target's fullUrl, id format, a profile-fixed Bundle.type — or the hint that fhir_finalize_bundle's bundle_type sets a free one —, document / message ordering, required elements and entry slices), likewise generated from the core specification and the StructureDefinition.

    Content repair (repair="content")¶

    fhir_finalize_bundle / fhir_finalize_resource take repair, default "content": besides the id normalisation above they correct content errors whose fix is uniquely determined; repair="ids" is exactly 1.1.0 / 1.5.0 (ids only). fhir_validate_bundle accepts repair="content" with normalize_ids=true. fhir_author_resources / fhir_assemble_bundle always apply the same rules (node-server/src/fhirRepair/ — one input, one verdict, one repair in every tool). Every correction is listed in changes[{path, from, to, rule, reason}]; a value that cannot be decided uniquely is left as written and listed in repair_issues[{path, rule, message, candidates}], the validator's error stays (and carries repair).

    v16 structure repairs (any IG, any depth): the max of every element is read from the declared profile's StructureDefinition (else core) — a repeating element given a single value → a one-item array, a max-1 element given a one-item array → the item, a meta.profile string → an array; an entry without resourceType whose meta.profile (array or string) names profiles of one resource type → that type; empty elements ({}, [], "", null, ele-1) removed; an Unrecognized property moved only when exactly one level up / down defines it. These are lossless reshapes: an error that appears after the repair only because the value can now be read (under the reshaped element, or the resource now validated against the meta.profile it declares, and profile-match errors of references to it) was hidden, not added, so the repair is kept; an inferred resourceType is withdrawn only by an unknown top-level property (a wrong type). On the example Bundles of the TWPAS 1.2.7 and TW Core 1.0.0 packages with these corruptions applied to every entry, the repaired Bundles are back to the examples' own error counts (node-server/scripts/v16-structure-eval/evalRepairs.ts).

    The official HL7 validator as the judge (v18 R1)¶

    Production runs one resident official validator_cli 7.0.1 per main IG (TW Core 1.0.0, TWPAS 1.2.7, IPS 1.1.0, EMPD 0.2.1; compose services hl7-validator-*, services/hl7-validator/). With OFFICIAL_VALIDATOR_URLS set, the structure, slicing, profile, invariant / FHIRPath, document and terminology errors of fhir_validate_bundle / fhir_validate_resource (and the "no new errors" guard of fhir_finalize_*) come straight from the official engine's OperationOutcome; MCP only adds suggestions, slice_match, pointer / patches and the content checks (grounding, record checks).

    Failed invariants: literal values and root causes (release v1)¶

    Every Constraint failed: <key> issue (official or built-in validator) carries invariant: - expression: the invariant's FHIRPath in the profile; human: its text as written (often Chinese). - literals: the literal values the expression names — systems, codes (with their system and the CodeSystem's display, telling which situation each code is for), values, formats (matches() regexes). - hint: the accepted values and the rule. - When the instance has a coding of that system with a code the rule does not accept, replace_code (or replace_system) suggestions become JSON patches; several candidates are ranked by how close their display is to the current code's meaning, and only the coding the rule is about gets them (e.g. the national-ID identifier, not the medical-record number). A coding the instance lacks is never invented. - v20.1: a replace_code patch also sets the display — replace / add display with the new code's display when it is known, else remove the old code's display; an accepted code under another (or no) system gets the rule's system (and its display when the coding has none); when the rule tests the identifier's own system (identifier.where(system = 'http://www.moi.gov.tw' …)) and accepts exactly one, the identifier whose type code the rule accepts gets a replace_system (patch on identifier.system).

    Cascades (Unable to find a profile match, an entry / reference slice not found) carry caused_by and root_causes: the errors at the end of the chain that are not cascades themselves (e.g. Composition → Encounter → Patient → pat-id-1).

    Auto-fix, ambiguous and "no new errors" (v19 R1)¶

    From fhir_finalize_bundle 1.14.0 (repair="content", the default) every structural error with exactly one correct fix is fixed by the tool itself, the rest is reported as ambiguous, and the errors after finalize are a subset of the errors before. Every rule comes from the StructureDefinitions / snapshots, the FHIR R4 specification and the validator's own messages — nothing IG-specific:

    • property renames (only when exactly one legal element matches and the value reads losslessly as its type): a choice suffix that is not an allowed type (doseNumberPositiveInteger → doseNumberPositiveInt, "1" read as 1), a choice stem without suffix (item → the one type the value's shape fits, itemCodeableConcept), singular / plural (periodUnits → periodUnit), MedicationStatement.dosageInstruction → dosage, STU3 children inside the R4 protocolApplied (doseSequence → doseNumberPositiveInt); several candidates → unchanged, reported ambiguous;
    • an entry written at Bundle level: fullUrl / resource on the Bundle itself (Bundle defines neither) → moved into a new last entry;
    • fixed / pattern (from 1.17.0, release v1): a missing fixed / pattern value may be filled in; an existing value that differs is never overwritten (by any fix category: fixed_pattern, shape, display, system_code …). A required element the profile fixes / patterns that the instance omits (Observation.status: minimum required = 1 with fixedCode: final) → that value is filled; for the validator's Value is 'A' but is fixed to 'B', A is the record's value (a preliminary result is not a final one): not changed, reported in ambiguous (category fixed_pattern, a message saying the record's value differs from what the profile requires; candidates are descriptions only — no automatic patch; a status element adds the hint that an unfinished result means the conversion should report insufficient_information), and the validator's error stays. The only exception is a pure representation difference — the same value in another JSON shape (["x"] / "x", surrounding whitespace) or another URI of the same code system (urn:oid:2.16.840.1.113883.6.1 / a trailing / for http://loinc.org), which is rewritten. The content repairs follow the same rule (fhir_validate_bundle with repair="content", the repairs author / assemble share): a coding slice the profile requires is not added when the same CodeableConcept already holds a coding of that system with another code that no other slice of the element takes (that is the record's concept) — it is reported instead. Bundle.type is the Bundle envelope, not a record value, and is still set to a profile-fixed type (see Bundle finalisation);
    • display: a code the profile pins by fixed / pattern (e.g. Composition.type, a section slice's code) → the valid display the validator names; an unpinned code whose display names another concept is not changed (whether the code or the display is wrong is not decidable) — ambiguous with both patches;
    • choice type: the profile allows one type and the value reads losslessly as it (valueString: "true" → valueBoolean: true) → renamed;
    • section narrative: the profile requires Composition.section.text and the section has entries → generated from those entries' names in the Bundle (no record content added);
    • the existing array / single value, narrative, system / code, id / reference (v9) and document completion repairs still apply.

    1.15.0 (v19 R1 round 2) adds these rules, again applied only when the fix is unique:

    • display (determined code): the code exists in its CodeSystem (the validator lists its valid displays), no other code of that CodeSystem is named exactly so (its display, or a designation fhir_normalize_code matches exactly), the written display shares at least half of its words with one of the code's names (or some words and the search ranks this code first), and no required binding rejects the code → the code's display, the written wording kept as CodeableConcept.text (when there is none). A display that shares (almost) nothing (ECOG performance status on the NYHA code) means the code itself is in doubt: not changed, ambiguous;
    • system (from the bound ValueSet): the element's bound ValueSet does not hold system#code but holds the same code with exactly the written display under one other CodeSystem (v3-ActCode#L 'Low' → v3-ObservationInterpretation) → that system;
    • a code in the wrong element: the code is not in its own element's required ValueSet and exactly one sibling element's required ValueSet holds it (AllergyIntolerance.type = 'medication' → category, criticality = 'unconfirmed' → verificationStatus) → moved there (as code / Coding / CodeableConcept per the target type, system and display from the ValueSet, an array when the target repeats); when the target already carries the code only the misplaced copy is removed; a target holding something else, or several fitting siblings → unchanged;
    • a string element written as an object: a string / markdown element given as an object with one string property (series: {text: "Tdap"}) → that string;
    • a code element written as a CodeableConcept: a Coding system that is the THO / core twin of the ValueSet's CodeSystem (terminology.hl7.org/CodeSystem/allergy-intolerance-category ↔ hl7.org/fhir/allergy-intolerance-category) counts as that CodeSystem;
    • a Reference one level down: a reference on a backbone with exactly one Reference child (Immunization.performer.reference → performer.actor.reference) → moved in; two candidates (Procedure.performer actor / onBehalfOf) → unchanged;
    • STU3 renames: also Composition.class → category;
    • duplicates: an STU3 name / wrong suffix (doseSequencePositiveInteger) whose one R4 element already holds the same value → the duplicate is removed; a different value → unchanged;
    • section entries of the wrong type: a resource type the section slice does not take (a MedicationStatement under Results) → moved to the one existing section that takes it; a type no section takes (the Medication itself under Medications) that another entry of the Bundle references (it stays reachable) → removed from the section; a section's last entry never moves (an empty section needs an emptyReason, a record fact).

    exposed_errors (finalize argument, default "strict"): after a rename / move, content the validator could not check while it was an unknown property is checked and may show errors. "strict" counts them as new and withdraws the rename; "allow_under_moved" treats errors located at / under the renamed or moved value's new location as hidden, not added: the rename is kept and those errors are listed in ambiguous. summary.exposed_errors reports the mode used.

    Response fields:

    • changes[] keep path / from / to / rule / reason and add pointer (RFC 6901, rooted at the Bundle as sent — a document reorder, dropped duplicate entries and entries moved in from Bundle level are mapped back to their sent positions), before, after, category (shape / narrative / display / unrecognized_property / system_code / ids_references / document_structure / fixed_pattern); moves / renames also carry moved_to (where the value is now); from 1.17.0 there is no no-op change (the same value at the same place);
    • ambiguous[{pointer, pointer_out?, pointer_note?, message, category, candidates[{description, patch?, patch_out?}]}]: what has several fixes or needs the record — withdrawn changes (with the change's patch), repair issues that could not be decided (display / code candidates, rename candidates, record values that conflict with a fixed / pattern value), references with no / several matching entries, and every R1-category error left after the fixes; patch is RFC 6902 that applies to the Bundle as sent (verified). From 1.17.0: pointer always resolves in the sent Bundle; pointer_out points into the returned (finalized) Bundle (only when it differs from pointer, e.g. an entry a document reorder moved) and resolves there too; an element that does not exist in that Bundle is named by its nearest existing ancestor and pointer_note says so; a candidate's patch_out is the same fix for the returned Bundle (only when paths or values differ; verified with patchApplies);
    • summary adds categories (changes per category), ambiguous, withdrawn, errors_before / errors_after (validator errors).

    No new errors: finalize validates the Bundle as sent and the finalized one (against the Bundle profile; by message, ignoring entry order and minted UUIDs). An error the finalized Bundle adds is traced to the change it is owed to (same location / same entry / Bundle level), that change is withdrawn and the pipeline runs again (≤ 3 rounds; not attributable → nothing is applied); withdrawn changes are listed in ambiguous. So a fix that makes previously unreadable content validated and thereby shows a new error (e.g. Dosage errors only visible after dosageInstruction → dosage) is not applied; the model gets it as a patch.

    Measured (node-server/scripts/parity/finalize-eval.ts, the 92 parity_v1 repro Bundles, structural errors without content checks): 1.14.0 1384 → 1104 (-20.2%); 1.15.0 (exposed_errors="strict") 1384 → 945 (-31.7%, 0 added): fixed_pattern 10 → 0, system_code 84 → 18, unrecognized_property 198 → 105, display 76 → 48, shape 60 → 35, ids_references 37 → 30, document_structure 42 → 42. What is left has no unique fix and is listed in ambiguous: document_structure is mostly a document without any Composition, or entries no section takes; ids_references are references to entries that are not in the Bundle; display is a written name that denotes another concept (the code itself is in doubt); unrecognized_property has several possible places or is an STU3 element R4 removed (vaccineProtocol, doseStatus). exposed_errors="allow_under_moved": 1384 → 965 (-30.3%), 45 of them errors under a renamed value's new location that the rename makes visible (new errors by the strict definition). 1.17.0 (release v1): 1384 → 956 (-30.9%, 0 added): existing different values are no longer overwritten (1.16.0 overwrote 10: 4 Observation.status preliminary → final, 6 category system / code) — those 10 fixed_pattern errors stay and are all listed in ambiguous; no-op changes 8 → 0; unresolvable ambiguous pointers 2 → 0.

    Directly applicable fixes (pointer / patches, v19 R3)¶

    Every issue of fhir_validate_bundle / fhir_validate_resource (issues and entries[i].issues, record checks included) also carries:

    • pointer: an RFC 6901 JSON Pointer rooted at the Bundle / resource exactly as the caller sent it, e.g. /entry/3/resource/code/coding/0/display. Converted from the validator's path (Bundle.entry[3].resource.code.coding[0].display); .value.ofType(string) → valueString, value[x], [url='…'], extension('…'), /*Type/id*/ comments and a stand-alone resource's root type are understood.
    • pointer_kind: element (the element the issue is about) or ancestor (the element does not exist — e.g. a missing required element — and the pointer is the parent to add it to).
    • patches (errors / fatals with at least one candidate): [{ops, reason, kind, confidence}]; ops is an RFC 6902 JSON Patch whose every path is a JSON Pointer into the sent Bundle (correct array indices, /- to append). Sources: suggestions[].patch (rename / move → move, replace → replace, add → add, remove → remove; a replace_fullurl also rewrites every reference that names the fullUrl), shape errors with one correct fix (wrap a single value in an array, unwrap a one-item array, remove an empty array / null / empty string / empty object, a profile-fixed string), the fixes of other issues (a misspelt / misplaced property renamed into a required element; an element empty only because none of its properties is recognised (ele-1); a slice / profile match blocked only by fixable errors), and closed-slice discriminator values (e.g. a Coding.system — from the IG, never from the record). Every candidate is applied to a deep copy of the sent Bundle before it is returned; one that does not apply is dropped. Candidates are alternatives — apply one. Record values are never invented: missing clinical content gets a pointer, not a patch.
    • entries[i].pointer: the entry's position in the sent Bundle (/entry/<index>).

    With normalize_ids=true the verdict is about normalized_bundle, whose document entries may be reordered (Composition first); pointers and patches are mapped back through the finalizer's entry permutation to the sent positions and checked against the entry's fullUrl (renamed fullUrls followed back through id_changes). In default mode the ID-class suggestions paths now also name the sent positions (previously the reordered ones). Existing fields (path, suggestions, severities, messages, valid) are unchanged.

    IG structure: Bundle blueprint and minimal skeleton¶

    Before writing a Bundle that must conform to a Bundle profile (a prior-authorization request, a document Bundle …), get the IG's structural knowledge from these two tools, then write the resources. Both read only StructureDefinition snapshots, the IG's ValueSets and the IG's own examples, and work for any installed IG (no IG-specific rules).

    derivable Computable without a record fact: references (the target entry's fullUrl), sequence / rank numbering, workflow defaults, the curated derivation rules, the system of a bound Quantity, insurance.focal, writing dates (Claim.created, authoredOn, recordedDate, extensions named like a recorded date …: the record's date for it, else the visit / document date); and (v20 R5) the record-derivable elements — the record determines them without writing the code: Condition.verificationStatus (the diagnosis field Dx / Impression / A: / 診斷 states it unhedged → confirmed, 疑似 → provisional, r/o / 待排除 → differential), Observation.interpretation (the H / L / HH / LL / ↑ / ↓ flag after the value, or the record's reference range: outside → H / L, inside → N), MedicationRequest.category (出院帶藥 → discharge, 門診 → outpatient, 住院 → inpatient; only when the binding holds such a code).     Only record rows need the record; a missing ig-constant, code-lookup, text-allowed or derivable value is never a reason to refuse. Elements outside the skeleton are optional.     1. Plan one key per resource (patient-1, enc-1, cond-1, obs-wbc …).
    2. Call fhir_get_authoring_fields(profile) once per profile.
    3. Call fhir_author_resources without context_id for the first batch and keep data.context_id; cross references are {ref: "<key>"} and may point at a key not authored yet (status refs_pending, resolved at assembly); cycles (Encounter.diagnosis ↔ Condition.encounter) are fine.
    4. Fix a status: invalid resource by resending the same key with merge: true and only the changed fields (null removes a field); issues carry key, field (your field name), path (FHIR path) and suggestions.

    Entry slices of the Bundle profile (bundle_slices)¶

    With bundle_profile, fhir_assemble_bundle (v16 R5, authoring/bundleSlices.ts, any IG) places every resource into the Bundle profile's entry slices before validation: the resource's declared meta.profile or the profile it was authored for decides the slice, else the only / clearly closest slice of its type; a resource authored for its slice's profile gets that profile in meta.profile when missing; entries follow the slice order when the slicing is ordered. bundle_slices reports entries (each key's slice and how it was decided), missing (slices below their min, with "author a … for profile …" guidance — resources are never invented), excess (over max) and unmatched (resources no slice takes under closed slicing), summarised in warnings. Decomposing the TWPAS / TW Core example Bundles into one key per entry (meta.profile removed, order reversed) and re-assembling puts every entry back into its slice with meta.profile restored and no more validation errors than the example; dropping a required slice's key is listed in missing (authoring/bundleSlices.ig.test.ts).

    Checking against the source record (grounding / completeness)¶

    Conformance-valid is not the same as faithful: a model can fill in a diagnosis code, date or dose the record never states, and the validator still passes. These tools compare a Bundle with the clinical record using deterministic rules (no LLM, no embeddings, no randomness). Code names are looked up in the local database only (ICD-10-CM / PCS, LOINC, SNOMED CT, RxNorm, CVX, IG CodeSystems); no external terminology server is called.

    Values the IG defines are not record facts (v17.2)¶

    A value the IG itself prescribes is not expected in the record, and will not be there. Grounding (G-UNGROUNDED, G-CONTEXT-*, G-STATED-ABSENT) and the record checks (ungrounded-value, information-absent, value-from-other-event, incomplete-value, insufficient-precision) exempt these values wherever they appear in a resource, and count them in grounding.exempt:

    • fixed[x] / pattern[x] of the declared profiles (meta.profile);
    • every value fhir_get_minimal_skeleton marks ig-constant, computed by the same function the skeleton uses, so the two cannot disagree. When the Bundle holds an administrative entity (Organization …), the ig-constants of the profiles the IG's examples use for that type are included too, e.g. the payer agency's name and OID. Since v17.4 an example-derived identity value (name, identifier, phone, address) counts only for a national payer / authority organization (detected as described under ig-constant above); the IG's example hospitals, clinics, labs, practitioners and patients are never exempt — a Bundle that copies the IG example hospital's name / identifier while the record says 臺大醫院 is reported by grounding and the record checks as before;
    • the answer literals a profile invariant allows for value[x] (e.g. value.ofType(string) = 'class1'). Only a value[x] string is exempt; a comparison on another element (such as gender = 'male') does not count.

    Quantities and bare numbers are never exempt. When one record line lists several medicines, a dose / frequency evidence quote belongs to the closest medicine named before it on that line; when that is the resource's own medicine there is no G-CONTEXT-LABEL.

    Versions and privacy

    • provenance carries tool, toolVersion, lexiconVersion / lexiconSha256, terminologyVersion and sourceSha256 (first 16 hex chars of the record's SHA-256). health_check reports tools_version, lexicon_version and lexicon_sha256.
    • The record text (source_text) and the site configuration are never written to logs, metric labels or provenance — only sourceSha256; malformed JSON request bodies are not logged either.

    The rules and the lexicon (tw-lexicon) follow Taiwanese clinical writing; fhir_check_completeness needs the caller to read the conversion target and pass targets — it does not parse natural-language targets. Results support review; they do not replace a clinician.

    Does the record actually provide it? (record checks)¶

    parity v2 (2026-11-01): a content error needs source_text. A call without source_text is a pure validation: every record-check finding is kept, but always as a warning (its evidence says no source_text), so it never changes the verdict the official validator gives.

    When a record deliberately lacks a piece of information, models still tend to "fill something in": "number not yet assigned" as the MRN, a month-only date as Encounter.period.start, a "to be ruled out" diagnosis as an established Condition. Such values can be well-formed — the string may even appear in the record — so both the validator and grounding pass them. Record checks are a post-validation layer (node-server/src/recordChecks/; like the fix suggestions it runs after the validator and never touches InstanceValidator, so the validator parity audit is unaffected) that reports "the record does not actually provide this information".

    record-fact-missing warning (content_checks_severity: "error" makes it an error) The record states it clearly but the element is empty: department → Encounter.serviceType; 共 28 天 → dispenseRequest.expectedSupplyDuration; dose / frequency / route on the drug's line; the patient's name — only elements the declared profile marks mustSupport / required, or that at least half of the IG's examples of the profile carry. Record-derivable facts (v20 R5, fhir_validate_bundle 1.31.0 / fhir_validate_resource 1.28.0): an item of the diagnosis field (Dx / Impression / A: / 診斷) → Condition.verificationStatus (unhedged confirmed, 疑似 provisional, r/o / 待排除 differential, read by the v15.3 diagnosis-slot parser); an H / L / HH / LL / ↑ / ↓ / * flag after the value or a reference range → Observation.interpretation (H / L / HH / LL, inside the range N, * alone A); a 出院帶藥 / 門診處方 / 住院醫囑 heading (else the record's only visit setting) → MedicationRequest.category (discharge / outpatient / inpatient) — reported wherever the profile has the element (any cardinality) and its binding holds the code (an IG ValueSet: the code whose display matches). The profile information is looked up by fhir_validate_bundle / fhir_validate_resource; nothing is reported without source_text

    How R5 finds values (recordChecks/recordValues.ts): only the record body (the 【轉換目標】 conversion target and the 院所設定 section never count); identifiers are also searched in the whole site_config. - Identifiers: NFKC, case-insensitive, without - _ . / spaces; whole tokens, contiguous joins of separator pieces, leading zeros, a label glued in front (MRN00775310). System-assigned identifiers (urn:uuid, Bundle / Composition / Claim identifiers) are not checked. - Dates: Gregorian, ROC (114/06/10, 民國114年6月10日), 年月日, slashes, month-day (with the record's years), English month names; times as HH:MM(:SS), 上午 / 下午 N 點 M 分, am / pm, HHMM right after a date; a value in another offset is also compared in the site timezone (site_config timezone:, default +08:00). Derivations: 入院第 N 天 / hospital day N / HD#N (admission + N−1), 術後第 N 天 / POD#N (operation + N), 第 N 天, N 天前 / 後, 昨天 / 前天 / 今天 / 隔天 / 次日 / yesterday / next day, N weeks / months before / after, a complaint duration (咳嗽 3 天 → 3 or 2 days before), a course on a treatment line (處方 … 7 天 → start + 6 or 7), N 年前 / N 年 (years), an age (54 歲 → birth year), "N minutes / hours later / before". Chinese numerals are read (入院第三天). Anchors are the record's own dates: the admission date for hospital-day expressions, the operation date for post-op ones, else a date on the same line, else the nearest preceding dated line (birth dates excluded); Encounter.period.start and Patient.birthDate must be dates the record states. Record-keeping times (authoredOn, recordedDate, issued …) only warn about an ungrounded date and their time is not checked; timestamps the tools / documents write themselves (Bundle.timestamp, Composition.date, Provenance.recorded …) are not checked. - Quantities: every number outside dates and times (so a 0 or a 14 is never grounded by "08:00" or "2025/03/14"), with its unit, Chinese numerals, 半, fractions; it must have a compatible unit (when both units are known), or convert (mass / volume / length / time, °F ↔ °C, glucose mg/dL ↔ mmol/L, 10^3/uL ↔ /uL), BMI from height and weight, an explicit product (500 mg x 2). Derived quantities (dispenseRequest.quantity, expectedSupplyDuration, Claim item quantities) also accept a product of numbers on one line and only warn when not found; reference ranges warn; denominators are not checked.

    How the primary Condition is decided (v15.3 R2, diagnosisSlot.ts primaryCondition): in order — (1) among the Encounter.diagnosis entries that reference a Condition of the instance and whose use is not CM (comorbidity), the lowest rank, else the first listed; only comorbidities → no primary; (2) otherwise the Conditions with category encounter-diagnosis (not problem-list-item): one → it; several → the first whose names match an item of the record's diagnosis slot, else the first listed; (3) otherwise the only Condition that is neither a problem-list item nor a comorbidity the record states outside its diagnosis slot (past history / plan / lab lines); (4) otherwise none and nothing is reported. Refuted / entered-in-error Conditions never count. Only that one Condition is examined.

    Grounding messages on codes (v15.3 R3, recordChecks/codeGrounding.ts): with source_text, the G-UNGROUNDED / G-VALUE-MISMATCH issues that grounding reports on a coded element (CodeableConcept / Coding, e.g. Condition.code = 'sct#…') in fhir_validate_bundle / fhir_validate_resource (and behind them fhir_author_resources / fhir_assemble_bundle) are rewritten: the message says that the code's meaning — text, displays, the terminology names the tool looked up (English + Chinese) and the ICD-10 code — was compared with the record lines (conversion target, site settings and family history excluded), since a record never writes the code itself; the issue carries closest_record_phrase = {text, similarity, section} (the closest record clause; similarity = grounding's weighted name containment with abbreviation and zh↔en bridge expansion, and for Chinese vs Chinese also the character-bigram Dice after concept-search normalisation, whichever is larger; null below 0.1), compared and grounding_code_check. It stays an error only with clear counter-evidence (contradicted): it is the code of the encounter's primary Condition, unrelated to every record clause (similarity < 0.25), and the record has a diagnosis slot whose every item is comparable with it (same language, both with ICD-10 codes, or a zh→en bridge translating ≥ 80 % of the Chinese; abbreviation-only items never) and dissimilar — the record states a different diagnosis. Everything else becomes a warning with downgraded_from: "error": a related phrase exists (related, similarity ≥ 0.25 — the code may name it in other words) or nothing can be concluded (uncertain: another language, no diagnosis slot, comorbidities, medicines, lab codes). When a downgrade leaves an entry / the grounding result without errors, entries[i].valid, groundingValid, valid and the grounding error / warning counts are recomputed from the remaining issues; data.record_checks.grounding_codes = {examined, warnings, errors}. fhir_check_grounding's own output is unchanged (it is compared byte for byte with the reference implementation).

    Chinese names of SNOMED codes (v15.3 R3 follow-up, grounding/snomedChinese.ts, fhir_validate_bundle 1.15.1 / fhir_validate_resource 1.12.1): SNOMED CT has English names only, so a Chinese diagnosis slot was never comparable and a wrong SNOMED primary diagnosis stayed uncertain. The comparison now also uses Chinese names derived from data (no hand-written translation list), each with a source and a confidence: IG zh designations / Chinese ValueSet displays (0.9 / 0.85); the SNOMED → ICD-10 map (snomed.icd10_map, map group 1, the highest-priority unconditional rule TRUE / OTHERWISE TRUE) → the ICD-10-CM Chinese name (target 0.75; 0.65 after conditional rules or when an ICD-10-CM child names it; 3-character category 0.6), without classification segments such as 未明示 / 無併發症 / 部位未明示; and the mined bilingual word pairs (fhir.term_thesaurus, source bilingual) applied word by word to the English names (only when ≥ 80 % of the content words translate; confidence 0.8 × coverage × the weakest word's Dice). Decision: Chinese names with confidence ≥ 0.5 join the closest-phrase comparison (related); only ≥ 0.6 make a Chinese slot item comparable; a comparable item names "something else" only when it is unrelated (< 0.25) to every English / Chinese name of the code and to every Chinese name of the mapped ICD 3-character category (0.3 — they can only prevent an error), and below 0.15 when only ICD-derived names make it comparable (the map is many-to-one and coarse); a slot ICD code in the mapped target's category is never different. Then it is an error (contradicted, the message names the Chinese name and its source), otherwise still a warning. The names used are listed in compared.chinese_names = [{name, source, confidence}]; neither fhir_check_grounding nor any other tool output contains them. 1.17.1 hardening: ICD Chinese names keep complete noun phrases only (qualifier prefixes such as 其他或未明示之 are removed whole; names starting with a function word / bound morpheme — 或氣喘, 性氣喘 — and tails one character short of another name are rejected); a mined-pair rendering that no ICD Chinese name of the concept corroborates is capped at 0.55 (related evidence only, never makes the slot comparable). Hierarchy guard: a diagnosis-slot item whose SNOMED concept (its ICD-10 code through the reverse snomed.icd10_map, or an identical ICD Chinese name) is the coded concept, an ancestor or a descendant of it (snomed.concept_ancestors) is never "something else" — lower respiratory tract infection vs 社區型肺炎 (J18.9) is a warning at most. Abbreviation-only slot items are judged on the record's own casing. The IG designation table loads in one cheap query (Chinese-language packages only, ~0.6 s on production), single-flight, refreshed in the background and warmed at startup; while the first load is running a request waits at most 2 s and then proceeds without IG names, with every Chinese name capped below the comparability threshold — results in that window may be warnings where later identical calls give errors, never the reverse.

    Empty shells (v15.4, recordChecks/emptyShell.ts, fhir_validate_bundle 1.16.0): instead of writing 「報告未出」 as the value, the model creates a resource without a value and writes the reason in note / dataAbsentReason / dosageInstruction.text. Such resources follow the "empty shell" row above. The absence predicates are classes of patterns (ABSENCE_CLASSES in lexicon.ts, matched after NFKC + lower case), not a flat word list, so 報告尚未回傳 / 結果還沒出來 / 待 CT 正式報告 / "result not back yet" share one pattern; negations (無溶血, no hemolysis), clauses that state a result (negative, normal, a number with a unit) and clauses that only say 追蹤中 / 原因不明 are not absences. 溶血 / 凝固 / hemolyzed count only for an Observation whose code needs a quantitative result (a serum-appearance result can be 「溶血」). A named diagnosis with 「待確認」 written as provisional is the correct encoding of a suspected diagnosis and is not reported. A diagnosis slot that says "A 與 B 尚難區分 / cannot differentiate" is unestablished (A written as established gets unconfirmed-as-confirmed). dataAbsentReason is no longer an R1 value slot (it is FHIR's way to say the value is absent); it is side-field evidence.

    Content gates: blocking and advisory (v20.1)¶

    With source_text, every content finding (grounding G-* and record-check code) carries a gate field:

    • blocking: may stop fhir_release_check, where it counts as a content error;
    • advisory: returned to the model as before (severity and message unchanged — fhir_validate_* keep it, and an advisory error still makes valid / groundingValid false), but it never stops the release.

    Rule (one registry, node-server/src/recordChecks/contentGates.ts): lexical / heuristic rules are advisory by default; a rule is blocking only with a precision ≥ 95% measured on realistic Chinese records over n ≥ 20 findings; warnings never block. Measured with node-server/scripts/content-fp/gold.ts (private gold Bundles with their records — every error there is a false positive — and negative cases with known findings: fabricated / changed values).     Fact coverage and the release gate¶

    Both tools are in the FHIR IG group (module gate ig, the same metrics / error boundary / heavy-tool concurrency cap as fhir_validate_bundle), fully deterministic (no LLM call), generic for every IG, and never log the record text, quotes or fact values.

    v20.2: only decidable conditions stop a release (evaluator decision)¶

    • No more lexical rules for meaning. Semantic checks (r/o, negation, stale values, code meaning, fact coverage) are the evaluator's model verifier's job; MCP reports these findings as advisory only.
    • fhir_release_check stops only on decidable conditions: the official validator's 0 errors (a complete official verdict), targets present, and G-UNGROUNDED on structured numbers / dates / identifiers (*.identifier.value, Quantity / integer / decimal values, range / ratio bounds, dates and periods). Free text (valueString, text, note, conclusion, names) does not count. Without targets: incomplete-input (facts are advice only).
    • Advisory informs, never instructs: an advisory error becomes severity: "warning" with advisory_from: "error" and no longer makes valid / groundingValid false; no remove suggestions or patches, and no message tells the model to delete content ("verify against the record" instead).
    • New fhir_release_check field advisories: fact coverage (fact-missing, quote-not-in-record, unusable-fact-written) and suspected-empty-bundle, reported, never stopping a release.
    • fhir_check_fact_coverage 1.2.0: a value in another value element of the fact's own resource is covered (reason_code: "found-in-other-element"); counts / sequence numbers / reference ranges (sequence, rank, frequency, period, count, referenceRange) only when the attribute names them; attribute may be a FHIR path (with resource type and indexes).
    • Every official-validator request carries validationTimeout (request timeout − 30 s): a validation that runs too long is stopped by the validator with a partial result, reported as unverified with checked_fully: false, instead of holding its single request thread.

    fhir_check_fact_coverage (v18 R3 = v20 R4)¶

    Input bundle, source_text, facts: [{item, attribute, value, quote, resource_type?}], package_id?, version?. Each fact is judged in order:

    1. The quote is in the record: compared after NFKC (full-width → half-width, lower case) with whitespace collapsed, then after the grounding normalisation (whitespace and most punctuation dropped); found neither way → quote_not_in_record (a fabricated basis).
    2. Usable: the clause around the quote (cut at ，,；;。, brackets and list enumerators) must not negate it (grounding NEG_CUES, prefix, within 10 characters), leave it not established (the record checks' cuesIn: 疑似, r/o, 待排除 …), mark it old / previous (OBS_HIST_CUES and the v17.4 stale vocabulary), pending / not applicable / not done (clausesOf absence classes) — else not_usable. Every cue is scoped (v20.1): a prefix cue governs only the value after it, a postfix cue only the value before it, never across a field label (X： / X:) — a cue in another field or inside a label does not count (the 疑 and 無 of 「處方疑義：無」 do not negate the drug after it); the "no" of Chart No., Lot No., ID No. abbreviates "number" and is no negation; when the value cannot be located in the quote, a cue in the middle of the quote (without in Type 2 DM without complications) qualifies another finding and does not negate the fact; Label：待補, where the value is the field label and the cue its content, still counts. A fact that is itself about that state (value 無 / negative / provisional / inactive …, or the cue in the value / attribute) stays usable. An unusable fact must not be written as a current value; when the conversion target needs it, answer insufficient_information.
    3. In a structured element: only entries of the fact's resource type are searched (inferred from item / attribute, e.g. drug / dose / route → MedicationRequest and the other medication resources, temperature / lab → Observation, diagnosis → Condition, visit → Encounter; or given as resource_type). text (Narrative, the text of an uncoded CodeableConcept, Dosage.text), note, a lone display, comment, patientInstruction do not count; HumanName / Address text does (also a name / address written as text only, v20.1), and so does the text of a CodeableConcept with a coded Coding (the record wording of that code); a phrase element (DiagnosticReport.conclusion, valueString …) counts when it contains the value (at least 4 characters); ContactPoint.value (phone) compares by digits ((02)2345-6789 = 02-2345-6789). Terminology equivalence:
    4. route: PO / 口服 / oral ↔ a Coding whose code, display or terminology name names the route (SNOMED 26643006 or an IG route ValueSet code);
    5. frequency: BID / 一天兩次 / Q12H ↔ Timing.repeat with the same administrations per day (frequency 2 / period 1 / periodUnit d), or timing.code;
    6. dates: ROC (114/06/02, 114年6月2日) and Gregorian spellings ↔ FHIR date / dateTime / Period, at the fact's precision;
    7. quantities: value and unit compared separately — the same number, and the record unit compatible with the Quantity's UCUM code or its unit (次/分, bpm ↔ /min, IU/mL ↔ [IU]/mL), or converted (0.5 g = 500 mg, cm ↔ m), any number spelling (12.50, Chinese numerals, thousands separators); every number of a multi-number value (120/80 mmHg) must be found; a unit-only fact (attribute 單位, value mg/dL) matches a Quantity with a compatible unit; numbers with units inside a valueString count too;
    8. numbers and dates count only in elements of the class the attribute names (v20.1): dose → doseAndRate / dose / doseQuantity, value → value[x] / component.value[x], start → period.start …; an attribute spelled as a FHIR element name (valueQuantity, period.start) means that element only. Counting / ordering / identifying integers (Dosage.sequence, rank, Timing.repeat.frequency / period …) are never a clinical value, and a referenceRange counts only when the attribute names a reference range. A value only in another element → missing with reason_code: "found-in-other-element" and found_elsewhere;
    9. encounter class and department: the ActCode aliases of Encounter.class (門診 ↔ AMB, 急診 ↔ EMER, 住院 ↔ IMP) and the department of serviceType (家醫科 ↔ Family practice); such lexicon equivalences count only when the attribute names that element (or gives no element at all);
    10. codes: Coding.code, or the Coding's display / terminology names (synonyms, Chinese names) equal or mostly overlapping;
    11. gender (男 / M ↔ male), booleans, other strings (equal after normalisation; HumanName also as family + given). Identifiers must be equal in full (醫字第035190號 ≠ 035190).

    Found → covered (found_at); else missing, with reason_code: "found-in-other-resource" and found_elsewhere when the value sits only in a resource of another type. 4. Suggested paths: a missing fact gets suggested_paths (child fields joined relative to the resource, e.g. Practitioner.name.text, never doubled into name.name.text) from the authoring fields of the matching entry's meta.profile (fhir_get_authoring_fields fields, detail full), ranked by the element the attribute names (route → dosageInstruction.route, days → dispenseRequest.expectedSupplyDuration …) first, then by whether the field's kind can hold the value; without an entry or profile, FHIR R4 base element names.

    fhir_release_check (v18 R4 + v20 R1)¶

    Input bundle, source_text, facts?, targets?: [{resourceType?, profile?, what?, code?: {system?, code}, min?, facts?: [index]}], site_config?, package_id?, version?, bundle_profile?, require_official? (default true). release: true only when all of these hold:

    1. Official validation, 0 errors: validated through the same pipeline as fhir_validate_bundle (the official engine when configured, see "The official HL7 validator as the judge"). The result must be official_verdict: true and not checked_fully: false; an MCP fallback, unverified codes or no official engine → not-officially-verified. require_official=false is for development only (the MCP verdict is accepted and validation.note says so), but checked_fully: false still stops the release (not-fully-checked). Release condition: parity 0 errors, checked_fully: true, extended_findings 0 errors. An extended error → extended-error (check: "extended"); unverifiable is only counted (validation.extended); a layer that did not finish → extended-incomplete.
    2. Grounding and record checks, 0 blocking errors: the same validation with source_text (errors with source: "grounding" / "record-checks"). Since v20.1 only errors with gate: "blocking" stop the release and count in content.grounding_errors / record_check_errors; advisory errors count in content.advisory_errors (with advisory_rules) and are returned to the model, but do not stop the release — see "Content gates".
    3. Complete fact coverage (with facts): missing → fact-missing / fact-in-other-resource; quote_not_in_record → quote-not-in-record; an unusable fact written into the Bundle → unusable-fact-written.
    4. Completeness (v20 R1): with neither targets nor facts completeness cannot be judged → incomplete-input, never released (v20.1). each targets item is in the Bundle at least min times (default 1; matched by resourceType, meta.profile, code), else missing-target. When facts name the missing item (facts indices, default the facts naming its resource type) and the record makes all of them unusable (negated, not established, pending, not applicable), insufficient-information is reported instead (next: insufficient_information); when no fact names it, it is a model omission: still missing-target, next: fix (evaluator decision, 1.0.1). A case not released in the end is reported as not convertible automatically. Without targets: the Bundle profile's (bundle_profile or meta.profile) required entry slices must be present (missing-entry-slice), and a Bundle with ≤ 1 content entry (Composition / MessageHeader not counted) while the facts name ≥ 2 resource types → suspected-empty-bundle.

    Output data: release, next (send | fix | insufficient_information), reasons: [{code, message, pointer?, count, check}] (check = validation / extended / content / facts / completeness; at most 25 issues of a kind are listed, the rest merged into one reason with its count), validation {completed, errors, warnings, source, engine, official_verdict, checked_fully, officially_verified, fallback_reason?, unverified?}, content {completed, source_text, grounding_errors, record_check_errors, warnings}, facts (the fhir_check_fact_coverage summary plus results; null without facts), completeness {entries, targets? | entry_slices?, fact_resource_types?, suspected_empty?}.

    Limitations: resource types and elements are inferred from zh / en keywords (resource_type overrides); a missing item that NO fact names is also taken as not provided by the record (insufficient_information), so a fact list that leaves it out is misread. Route / frequency equivalence rests on the grounding lexicon and the terminology names; an IG-specific code whose display does not name the route is not recognised.

    Two layers of results: issues and extended_findings¶

    A validation result has two independent layers:

    • Parity layer: issues and valid reflect HL7 validator_cli 7.0.1 only, and never add an error it does not have. checked_fully means exactly "every check it would do was done".
    • Extended layer: extended_findings reports what the local data can prove where validator_cli only warns. It is never part of issues, does not affect valid or checked_fully, and the whole field is absent when there is nothing to report. fhir_validate_bundle, fhir_validate_resource (in data), fhir_finalize_resource (in data.validation) and fhir_finalize_bundle carry it.

    Shape: extended_findings: {summary: {errors, unverifiable, incomplete?}, findings: [{kind, severity, path, message, system?, code?, held_as?, profile?, fix?: {action, replace_with?, candidates?}, reason?, count?}]}. incomplete: true means the layer did not finish (a lookup failed, more than 5,000 Codings) and is not a pass.

    code-not-in-held-codesystem error Coding.system is a spelling validator_cli does not know, the CodeSystem is held here under another spelling of the same canonical (held_as: http / https, a CodeSystem published under its /ValueSet/ URL), and the complete copy does not have the code
    unresolvable-profile error meta.profile resolves to no StructureDefinition of the IG closure; carries a fix
    malformed-profile error meta.profile is not a canonical at all; carries a fix
    no-local-data unverifiable A system validator_cli cannot check either and with no local data (or only an incomplete copy, see reason). One finding per system, count = Codings; counted, does not block a release

    "Held locally" respects edition completeness: a fragment, an excerpt (a declared count above the concepts it carries, or a description saying it holds only part of the codes on a copy under 1,000 concepts; full copies carry that sentence too, so it is not believed on a large one), an older edition (icd.editions.complete etc.) or a copy outside the IG closure never yields "code not found", only unverifiable.

    Where the terminology server ends and unverifiable begins: validator_cli sends a system to tx.fhir.org according to the server's published TerminologyCapabilities (ValueSetValidator.preferServerSide → TerminologyClientManager.supportsSystem). That URI list is bundled as node-server/data/terminology/tx-codesystems.json.gz. With no local data: a system on the list is checked by validator_cli and cannot be here → checked_fully: false; a system not on the list is only the UNKNOWN_CODESYSTEM warning there too → checked_fully: true plus a no-local-data finding. A ValueSet not found keeps checked_fully: false, because validator_cli asks the server for it (BaseWorkerContext.findTxResource) and the server's ValueSets are not known here.

    meta.profile repair: fhir_finalize_bundle (rule meta-profile, listed in changes, counted in summary.meta_profile) and fhir_finalize_resource (profile_changes) correct a value only when it maps to exactly one canonical among the closure's profiles of the same resource type: (1) it differs only by |version, case, scheme, a trailing slash or .html; (2) its last URL segment is a profile's id; (3) on the same base, the nearest id by edit distance (≤ 5 and at most half its length), strictly nearer than the runner-up. Several candidates at the same rank: no repair, only fix.candidates. Errors that appear once the right profile is checked were hidden before, not added by the repair: the repair stays and the errors are reported.
